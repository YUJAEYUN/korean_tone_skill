# 자기개선 시스템 설계 문서 (PRD)

이 문서는 `korean-plain-writer`가 스스로를 개선하는 전체 구조를 정의한다.
"어떻게 실행하는가"는 `HARNESS.md`·`improvement-protocol.md`에 있고, 여기서는
"왜 이렇게 만들었는가"와 "다음에 뭘 바꿀 것인가"를 다룬다.

## 1. 문제

가중치를 재학습할 수 없는 상태에서, 정답이 하나로 정해지지 않는 "좋은 글"의
품질을 어떻게 측정하고 개선하는가. 두 가지가 동시에 필요하다.

1. **측정**: 개선 전/후를 비교할 기준. 절대 점수는 평가자마다 흔들려서 신뢰할 수
   없으므로 쌍대 비교(champion vs challenger, 어느 쪽이 나은가)를 쓴다.
2. **개선**: 모델 파라미터 대신 하네스(스킬 지침, 참조 파일, 검증 규칙)를
   바꿔서 품질을 높인다.

## 2. 지금까지 실제로 겪은 한계

세 번의 개선 라운드(round1, round2, round2b)를 실제로 돌리면서 같은 문제가
반복됐다.

- **매 라운드가 표본 부족으로 끝났다.** `policy.json`의 최소 기준(사례 6개,
  비교 20건)을 채운 라운드가 하나도 없다. round1·round2b는 자동 판정이
  `insufficient_evidence`인 채로 사람이 diff를 직접 읽고 수동 승인했다.
- **라운드가 끝나면 그 라운드의 사례와 실패 관찰이 사라졌다.** 다음 라운드는
  다시 사례 0개에서 시작했다. 누적되는 증거가 없으니 표본 부족이 반복될
  수밖에 없었다.
- **사람 채점자가 한 번도 없었다.** 자가 채점(같은 세션)과 독립 Agent 채점
  (다른 모델, `HARNESS.md`의 "독립 채점자 확보" 절차)만 있었다. round1에서는
  둘이 일치했지만, round2에서는 자가 채점과 독립 채점이 정반대로 갈렸고 원인은
  사례 설계 결함이었다 — 사람이 실제로 봤다면 더 일찍 잡았을 종류의 문제다.
- **가설을 고르는 근거가 그때그때 달랐다.** round1은 이전 파일럿에서 우연히
  발견한 결함, round2·round2b는 외부 프로젝트(im-not-ai) 리서치였다. 둘 다
  정당한 출처지만, 우리 자신의 실행 기록에서 반복되는 실패를 체계적으로
  모아서 우선순위를 정한 적은 없었다.

## 3. 구조

```
실패 로그(failure-log.jsonl)
    │  라운드가 끝날 때마다 관측된 실패를 태깅해서 누적
    ▼
메커니즘 확인 (사람이 로그를 훑어보고 반복되는/명확한 것을 고름)
    ▼
가설 하나 선정 → experiment.yaml 작성 (improvement-protocol.md)
    ▼
challenger 생성 (최소 변경)
    ▼
블라인드 평가: 사람(주) + 독립 Agent(보조, 같은 근거로 수렴하는지 확인)
    ▼
held-in(dev) · held-out(validation) 양쪽에서 이중 비퇴화 확인
    ▼
승격 판정: product-contract.md의 "사람의 역할" 3단계 정책
    ▼
CHANGELOG·promotion-manifest 기록 + 실패 로그에 status 갱신
```

이 루프는 논문 하나를 그대로 옮긴 게 아니라, 우리가 겪은 문제(위 2절)에 맞춰
필요한 조각만 가져온 것이다. 어떤 조각을 왜 가져왔는지는 각 절에 적는다.

## 4. 역할

| 역할 | 누가 | 무엇을 |
|---|---|---|
| 개선 제안 | 개선 AI(Claude Code 세션) | 실패 로그를 보고 가설 하나를 고르고, challenger를 최소 변경으로 만든다 |
| 주 채점자 | 사람(사용자) | 블라인드 쌍을 보고 어느 쪽이 나은지 고른다. 여러 주제로 직접 글을 쓴다 |
| 보조 채점자 | 독립 Agent(다른 모델) | 같은 블라인드 쌍을 가설·diff 없이 재채점해서 사람 채점과 수렴하는지 확인 |
| 승인자 | 사람(사용자) | `product-contract.md`의 3단계 정책에 따라 최종 승격 여부를 정한다 |

사람이 채점자와 승인자를 겸하지만 역할은 분리돼 있다 — 채점은 "어느 쪽이
낫나"(내용 판단), 승인은 "이 증거로 배포해도 되나"(리스크 판단)다.

## 5. held-in / held-out 이중 비퇴화 규칙

기존 `cases/dev.jsonl`(개선자가 보는 사례, 27개)을 held-in으로,
`cases/validation.jsonl`을 held-out으로 그대로 쓴다. 새 스플릿을 만들지
않는다.

**승격 후보가 되려면**: dev·validation 양쪽 다 challenger 승률이 champion보다
낮아지지 않고, 적어도 한쪽은 실제로 개선돼야 한다. 한쪽을 희생해서 다른 쪽만
좋아지는 트레이드오프는 승격 후보에서 제외한다.

지금은 `static-grade`/`make-blind`/`report`를 dev와 validation에 각각 한 번씩
수동으로 돌려서 확인한다(구체적 명령은 `HARNESS.md`). 자동화하지 않는 이유는
8절 참고.

## 6. 실패 로그

`failure-log.jsonl`. 라운드가 끝날 때 관측된 실패를 다음 필드로 남긴다.

- `cause`: 무엇을 실패했나 (검증기가 최종적으로 거부한 이유)
- `causal_locus`: 실패에 관련된 스킬 동작의 어느 지점이 원인인가
- `mechanism`: 추상화된 메커니즘 태그. 표면적으로 같은 실패(예: 의미 왜곡)라도
  원인 메커니즘이 다르면 다른 태그를 쓴다
- `reason_tags`: `improvement-protocol.md`의 기존 6종
  (meaning/voice/naturalness/fluency/overediting/instruction) 재사용
- `status`: `open` 또는 `addressed:<라운드 이름>`

다음 라운드의 가설은 `status: open` 항목을 메커니즘별로 훑어보고, 가장 많이
반복되거나 원인이 가장 명확히 분리되는 것을 고른다. 지금은 사람이 눈으로
본다(자동 클러스터링을 안 하는 이유는 8절).

## 7. 사람 평가 절차

세부 절차는 `human-rating-protocol.md`. 핵심만 요약하면: 매 라운드 새 주제로
직접 글을 쓰고(과거 사례 재사용 금지, validation 회전 규칙과 같은 이유),
`make-blind`가 만든 `ballots.jsonl`만 받아서(어느 쪽이 champion인지 모르는
채로) 판단하고, `votes-human-<이름>.jsonl`에 `reason_tags`와 함께 남긴다.

## 8. 지금 안 만드는 것 (의도적 보류)

아래는 빠뜨린 게 아니라, 지금 규모에서는 이득보다 비용이 크다고 판단해서
미룬 것이다. 조건이 바뀌면 다시 검토한다.

| 항목 | 왜 지금 안 하는가 | 언제 재검토하는가 |
|---|---|---|
| 메커니즘 자동 클러스터링 | 로그가 몇 건 안 쌓인 상태에서 임베딩 유사도 등으로 자동 묶으면 과적합 위험이 크다 | 로그가 수십 건 쌓인 뒤 |
| K개 병렬 후보 제안 | 사람이 매 라운드 diff를 직접 읽는 구조에서 검토 부담이 K배로 늘어난다 | 승격 대부분이 "승인 없이 진행"(`product-contract.md`)으로 넘어간 뒤 |
| 이중 비퇴화 검증 자동화 | `policy.json`/`eval_harness.py`를 건드리는 대신 사람이 명령을 두 번 돌리는 수준으로 시작한다 | 이 절차가 여러 라운드 안정적으로 돌고 나서 |
| `korean-writing-orchestrator/eval`로 확장 | 이번 재설계는 `korean-plain-writer/eval/`에만 적용한다 | 이 구조가 검증되면 orchestrator의 `HARNESS.md`가 이미 하듯 "복제하지 않고 참조"하는 방식으로 |

## 9. 관련 문서

- `HARNESS.md`: 실행 명령, 데이터 형식, 채점자 확보 절차
- `improvement-protocol.md`: 라운드 진행 절차, 실패 로그 확인 → 가설 선정
- `product-contract.md`: 우선순위, 절대 실패 게이트, 사람의 역할(승인 정책)
- `human-rating-protocol.md`: 사람 채점자 절차
- `failure-log.jsonl`: 누적 실패 기록
