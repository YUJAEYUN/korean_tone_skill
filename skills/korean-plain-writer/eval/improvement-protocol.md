# 후보 스킬 개선 프로토콜

이 절차는 추론 모델이 아이디어를 내고 스킬을 개선할 때 사용한다. 목표는 많은 규칙을 추가하는
것이 아니라 관측된 실패를 가장 작은 변경으로 고치는 것이다.

## 입력

개선자에게 다음만 제공한다.

- `product-contract.md`
- 현재 champion 스킬과 관련 참조 파일
- `cases/dev.jsonl`의 입력 및 실행 결과
- 사례별 실패 태그와 평가자의 근거
- 비용·지연 같은 운영 제약

비공개 테스트, 블라인드 정답 키, 최종 승격 점수는 제공하지 않는다. validation 결과로 한 번
수정한 뒤에는 해당 validation 사례를 dev로 옮기고 새 validation을 확보한다.

## 한 라운드의 산출물

개선자는 먼저 아래 실험 기록을 작성하고 challenger만 수정한다.

```yaml
hypothesis: 관측된 실패가 생긴 구체적인 이유
evidence_cases: [dev-case-id]
proposed_change: 추가·수정·삭제할 최소 변경
expected_effect: 좋아질 사례 범주
regression_risk: 나빠질 수 있는 사례 범주
files_allowed: 수정이 필요한 후보 파일
stop_condition: 같은 실패가 재현되지 않거나 두 번의 패치가 효과가 없으면 중단
```

서로 다른 가설을 한 후보에 섞지 않는다. 규칙 추가보다 기존 규칙의 범위 축소, 충돌 제거,
예시 교체를 우선한다. 평가 점수를 올리기 위한 문구나 특정 테스트 문장을 스킬에 넣지 않는다.

## 평가와 판정

별도의 실행자가 같은 모델·설정·trial 수로 champion과 challenger를 생성한다. 결정적 검사를
먼저 실행하고, 통과한 결과만 블라인드 쌍대평가한다. 평가자는 개선 가설과 diff를 보지 않는다.

`eligible_for_human_review`가 나와도 자동으로 배포하지 않는다. 사람은 다음을 확인한다.

- 가설과 무관한 대규모 변경이 섞이지 않았는가
- 평균에 가려진 장르별 회귀가 없는가
- 의미 게이트와 채점자 불일치 사례가 타당한가
- 스킬 지침이 중복되거나 서로 모순되지 않는가
- 증가한 비용과 지연이 품질 향상에 비례하는가

## 승격과 릴리즈 노트

사람이 승격을 승인하면 그 자리에서 세 가지를 함께 한다. 순서를 나누지 않는다 —
스킬 변경과 노트가 따로 놀면 다음 라운드에서 "뭐가 왜 바뀌었는지" 다시 diff를
읽어야 한다.

1. `challenger.diff`를 `skills/korean-plain-writer/SKILL.md`(champion)에
   그대로 적용하고 `metadata.version`을 올린다.
2. `CHANGELOG.md`에 새 버전 항목을 추가한다. 다음을 반드시 포함한다.
   - **무엇이 바뀌었는가**: diff 요약(규칙 나열이 아니라 실제 추가/삭제/수정).
   - **왜 필요했는가**: 이 변경을 촉발한 구체적 관측(dev 사례, 이전 파일럿
     결과 등). `hypothesis`를 그대로 옮겨써도 된다.
   - **검증**: 몇 건 비교했는지, 후보가 이겼는지, 무관한 사례에 회귀가
     있었는지, `report.md`의 판정 라벨(`eligible_for_human_review`/
     `insufficient_evidence`/그 외).
   - **알려진 한계**: 표본 크기, 자기채점 여부, 판정이 정책 기준에 못 미친
     채 사람이 수동 승인한 경우 그 사실 자체. 좋아 보이려고 한계를 생략하지
     않는다.
   - 해당 라운드 디렉터리(`eval/runs/<날짜-이름>/`) 경로.
3. `promotion-manifest.json`(모델·스킬 해시·Git 커밋·승인자)을 라운드
   디렉터리에 남긴다. `HARNESS.md`의 승격 기록 요구사항과 같다.

판정이 `insufficient_evidence`인데도 사람이 승격을 결정한 경우, 이는 정책
임계값을 낮춘 게 아니라 사람의 별도 판단이라는 점을 CHANGELOG와
promotion-manifest 양쪽에 명시한다.

승격하지 못한 후보는 현재 스킬에 일부라도 자동 병합하지 않는다. 유용한 실패 사례와 실험
결과만 보존한다.

## 사람 취향 학습

사람의 A/B 선택에는 가능한 경우 `reason_tags`를 함께 남긴다.

- `meaning`: 의미가 달라짐
- `voice`: 내 말투가 사라짐
- `naturalness`: 기계적이거나 상투적임
- `fluency`: 문법이나 연결이 어색함
- `overediting`: 필요 이상으로 고침
- `instruction`: 요청한 범위나 형식을 어김

개선자는 단일 선택을 보편 규칙으로 만들지 않는다. 같은 이유가 여러 실제 사례에서 반복될 때
사용자 취향 후보로 제안하고, 서로 충돌하는 선택은 장르·격식·독자 조건으로 분리한다.
